# P3.1 — Telegram update_id 멱등 처리

```
목표: Telegram 웹훅의 중복 처리를 막는다. 다른 기능은 건드리지 않는다.

배경: 텔레그램은 웹훅에 2xx 응답을 제때 받지 못하면 같은 update 를 반복 재전송한다.
현재 doPost 는 재전송을 새 메시지로 처리해 Transactions 에 같은 행이 여러 개 생긴다.

읽을 파일: CLAUDE.md, apps-script/src/Webhook.js, apps-script/src/Telegram.js,
apps-script/src/Config.js (SHEETS 상수만), docs/SHEET_SCHEMA.md (Log 탭만).

작업:
1. Webhook.js 의 doPost 에서 token 검증 직후, update 파싱 직후에 update_id 멱등 검사를 추가한다.
   - key = 'tg_update_' + update.update_id 를 CacheService.getScriptCache() 에서 조회.
     이미 있으면 아무 처리 없이 즉시 ContentService.createTextOutput('ok') 를 반환한다.
   - 없으면 처리 시작 전에 cache.put(key, '1', 21600) 을 먼저 기록한 뒤 진행한다 (6시간).
   - 캐시가 비워졌을 가능성에 대비해 캐시 미스 시 Log 탭의 최근 200행에서
     같은 update_id 가 있는지 한 번 더 확인하고, 있으면 스킵한다.
   - 중복 판정 로직은 순수 함수 isDuplicateUpdate(updateId, cacheHit, recentLogIds) 로
     apps-script/src/Dedupe.js 에 분리하고 module.exports 가드를 붙인다.
2. Log 탭에 update_id 열을 추가한다.
   - Config.js 의 SHEETS.Log 헤더와 docs/SHEET_SCHEMA.md 를 함께 갱신한다.
   - Setup.js 의 헤더 검증이 기존 Log 탭에 update_id 열이 없을 때 throw 하지 않고
     마지막 열 뒤에 추가하도록 바꾼다. 다른 탭의 검증 동작은 그대로 둔다.
   - doPost 가 Log 에 쓸 때 update_id 를 함께 기록한다.
3. Telegram.js 에 getWebhookInfo() 를 추가한다. tg('getWebhookInfo') 결과 JSON 을 Logger.log 로 출력한다.
4. 처리 순서(시트 기록 → 회신)는 바꾸지 않되, 회신을 위한 tg 호출은 try/catch 로 감싸
   회신 실패가 200 반환을 막지 않게 한다.
5. apps-script/tests/dedupe.test.js 에 테스트 3개 추가:
   신규 id → false, 캐시 히트 → true, 캐시 미스이지만 recentLogIds 에 존재 → true.
6. docs/SETUP.md 의 P3 절 끝에 "회신이 여러 번 오면 getWebhookInfo 를 실행해
   last_error_message 를 확인한다" 한 줄을 추가한다.
7. 이 프롬프트를 claude/prompts/P3.1.md 로 저장하고 STATUS.md 를 갱신한다.

검증:
- cd apps-script && npm test 전부 통과 (기존 41개 + 신규 3개).
- node --check apps-script/src/*.js 통과.
- grep -l "SpreadsheetApp\|CacheService" apps-script/src/Dedupe.js 결과가 비어 있어야 한다.
- doPost 에서 update_id 검사가 token 검사 다음 두 번째 게이트인지 코드를 인용해 보고한다.
```

## 구현 메모
- `SHEETS.LOG` 에 `extendable: true` 를 붙이고, `setupSheet()` 은 이 표시가 있는 탭에 한해
  실제 헤더가 기대 헤더의 앞부분과 일치하고 뒤쪽만 모자랄 때 `appendMissingHeaders` 로 이어붙인다.
  `isHeaderPrefix` 는 문자열이 아니라 배열을 원소 단위로 비교한다. 문자열 접두 비교는
  `a|b` 가 `a|bc|d` 의 접두가 되어 다른 헤더를 같은 것으로 볼 수 있다.
- 캐시 미스일 때만 `recentLogUpdateIds(200)` 을 읽는다. 캐시 히트면 시트를 읽지 않는다.
  `update_id` 가 없는 update(테스트 호출 등)는 멱등 판정을 건너뛰고 정상 처리하며,
  `tg_update_undefined` 같은 키를 캐시에 넣지 않는다.
- `cache.put` 은 처리 시작 **전에** 한다. 처리 도중에 재전송이 도착해도 두 번째 실행이 곧바로 걸린다.
- 회신 래퍼는 `safeSend` / `safeEdit` / `safeAnswer` 세 개다. 아울러 `tg()` 안의
  `getSecret('BOT_TOKEN')` 호출을 try 블록 안으로 옮겨, BOT_TOKEN 미설정도 예외로 새어나가지 않게 했다.
- 시트 기록 → 회신 순서는 그대로다. 회신이 실패해도 원장 기록은 이미 끝난 상태다.
